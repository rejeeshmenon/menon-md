# Research: Should menon.md expose an MCP server?

Date: 2026-09-22
Scope: live web research only, real sources cited. No file outside `docs/reviews/` was modified.

## What already exists (read before researching, so nothing below duplicates it)

From `src/content/cv.yaml`, `src/pages/api/chat.ts`, `src/chat/prompt.ts`:

- **Single source of truth**: `cv.yaml` generates every surface (HTML, JSON-LD, `/llms.txt`, `/llms-full.txt`, `/cv.json` JSON Resume, chat grounding, OG image). No fact appears anywhere that is not in this file.
- **`/api/chat`**: an Astro API route (`prerender = false`) on the Cloudflare Worker built by `@astrojs/cloudflare`. It streams SSE from Claude Haiku 4.5, with the *entire* CV markdown injected into the system prompt on every call (full-context grounding, no RAG, no vector store). Guards already in place: same-origin check, Zod-validated body, per-IP hourly rate limit via `CHAT_KV` that fails closed, 90-day-TTL Q&A logging with hashed IP only.
- **`prompt.ts`**: a strict, well-built grounding contract — cite every claim to a CV section heading, fixed refusal string for anything not in the CV, no persona changes, no medical advice, third person, no em/en dashes, prompt-injection resistance for untrusted visitor input (rule 6), and an explicit "job-fit comparison" mode (rule 9) that already does exactly what a `why_fit_for_role` tool would do, just conversationally.
- **Hosting**: Astro's Cloudflare adapter (`@astrojs/cloudflare` 14.x) compiles the whole site to a single Cloudflare Worker with `main: "@astrojs/cloudflare/entrypoints/server"`, static assets served from `./dist`, `nodejs_compat` on, one KV namespace (`CHAT_KV`), no Durable Objects. `/api/chat` is just another Astro API route inside that Worker.

This matters for the recommendation below: this is *not* a bare Cloudflare Workers project using the Agents SDK scaffolding — it is an Astro app on the Cloudflare adapter, so anything added has to be a plain Astro API route, not a `createMcpHandler`/`McpAgent` Worker entrypoint, unless the routing is restructured.

## 1. State of "CV/portfolio as MCP server" in 2026

The pattern is real, live, and has moved from novelty to a small but genuine micro-genre — but it is still hobbyist-scale, not an industry practice hiring teams participate in.

Confirmed real examples found via search:

- **`Mrinank-Bhowmick/MCV`** — "MCP server for my CV/Resume," built on Cloudflare Workers + Durable Objects, SSE transport at `mcv.bhowmickmrinank.workers.dev/sse`, exposes whole-resume and section-level tools (contact, education, projects). Confirmed via direct repo fetch: **0 stars, 0 forks, 1 watcher** — a working template, not an adopted tool.
- **`aarangop/resume-mcp`** — job-search assistant MCP that tailors a resume against a JD and produces Markdown/LaTeX output. This is a candidate-side *tool for using* AI on your own resume, not a CV exposed *to* other agents.
- **`theluckystrike/mcp-resume`** — resume/cover-letter generation from a fixed profile, "never invented," explicitly built to avoid hallucination — same discipline this site already has in `prompt.ts`, but for document generation, not Q&A.
- **`jsonresume/mcp`** — updates a JSON Resume (the same schema this site already emits at `/cv.json`) by analyzing a codebase and writing project entries back to a GitHub Gist. Modest real adoption: 63 stars, 11 forks — the most-used resume-MCP project found, and it is a write tool for the candidate's own workflow, not a read surface for recruiters.
- **A live, in-progress design discussion**: GitHub issue `HarshdipSaha/HARSHDIPSAHA.github.io#62`, "MCP server: public, read-only Model Context Protocol server for portfolio context." This is the closest real precedent to what's being asked here — same shape (public, read-only, Cloudflare Workers, single source of truth feeding both the site and the MCP layer so they "can never silently disagree"), proposing exactly two tools (`searchProjects`, `getProfile`). As of the fetch, **it is a spec with no server code written yet** — evidence the idea is being seriously discussed by builders in this exact niche, not evidence it has shipped or been used by a recruiter.
- Recruiting-industry MCP servers (Greenhouse MCP, Metaview, Recruo, Spott, Hirevire, HeroHunt) exist and are real, but they connect an agent to the *recruiter's own ATS and interview data* — candidate scorecards, transcripts, pipeline status. None of the recruiting-MCP material found describes a workflow where a recruiter's agent reaches out to a *candidate's personally hosted* MCP server. That direction of connection was not found anywhere in the research.

**Honest evidence-gap flag**: no source found — not a case study, not a hiring-manager blog post, not a Hacker News thread with a hiring-side reaction, not an Anthropic/OpenAI/DeepMind statement — describes an AI company's hiring team actually connecting to, querying, or even being aware of a candidate's personal MCP server during evaluation. A Hacker News "Show HN: My AI-Native Resume" thread turned up in search but the search tool returned no substantive commentary from it worth citing without a direct fetch, and no other discussion surfaced hiring-side reactions at all (positive or negative). Treat "hiring managers query candidate MCP servers" as **unverified and currently untrue as a practice**, not merely under-evidenced.

Sources: [Resume MCP Server (LobeHub)](https://lobehub.com/mcp/rajg1011-resume-mcp-server), [MCV on GitHub](https://github.com/Mrinank-Bhowmick/MCV), [aarangop/resume-mcp](https://github.com/aarangop/resume-mcp), [theluckystrike/mcp-resume](https://github.com/theluckystrike/mcp-resume), [jsonresume/mcp](https://github.com/jsonresume/mcp), [portfolio-mcp-server on PyPI](https://pypi.org/project/portfolio-mcp-server/), [GitHub issue #62](https://github.com/HarshdipSaha/HARSHDIPSAHA.github.io/issues/62), [Greenhouse MCP blog](https://www.greenhouse.com/blog/ai-tools-for-recruiting-greenhouse-mcp), [Metaview MCP blog](https://www.metaview.ai/resources/blog/mcp-connector-recruiting-stack), [Best MCPs for Recruiting 2026 (HeroHunt)](https://www.herohunt.ai/blog/best-mcps-for-recruiting-in-2026/).

## 2. What it would concretely take to build a real one

**MCP spec, current state**: The active specification is **2026-07-28**, described by the MCP project itself as the largest revision since launch, delivering on the 2026 roadmap goal of "a stateless core that scales on ordinary HTTP infrastructure." Concretely for transport:

- **Streamable HTTP** is now the only recommended transport for new remote servers: a single `/mcp` endpoint, each client message is an HTTP POST, and the response is either a plain JSON object or a request-scoped SSE stream (not a long-lived one).
- The 2026-07-28 revision **removed protocol-level sessions and the `Mcp-Session-Id` header**, and **removed SSE stream resumability/redelivery** (`Last-Event-ID`) from Streamable HTTP. The protocol is now explicitly stateless at the transport layer; statefulness, if needed, is an application concern, not a protocol one.
- Old bare **SSE transport** (2024-era, two endpoints, long-lived connection) is legacy/deprecated. Building on it in 2026 would mean shipping an already-superseded pattern — notably, the `Mrinank-Bhowmick/MCV` example above still uses `/sse`, which is now the outdated approach.
- Plain **stdio** transport is for local/desktop MCP servers launched as a subprocess; irrelevant for a public website.

Sources: [The 2026 MCP Roadmap](https://blog.modelcontextprotocol.io/posts/2026-mcp-roadmap/), [2026-07-28 spec: transports](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports), [2026-07-28 changelog](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/changelog.mdx), [2026-07-28 release-candidate post](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/).

**Cloudflare Workers support**: This is genuinely well documented and current, not speculative.

- Cloudflare's Agents SDK added `createMcpHandler()` (introduced November 2025) specifically for **stateless** MCP servers, built on an experimental stateless mode in the MCP TypeScript SDK — this is now the recommended path for new servers over the older, session-oriented `McpAgent`/Durable-Objects pattern.
- Cloudflare worked directly with the MCP TypeScript SDK maintainers in early 2026 to **replatform the SDK from Node.js onto Web Standards**, specifically to improve interoperability with Workers (and Bun/Deno).
- Cloudflare's own docs confirm Streamable HTTP is "the recommended approach for new MCP servers," and that public, unauthenticated servers are a first-class supported pattern (the `remote-mcp-authless` template), alongside an OAuth-gated path for servers that need identity.
- A production-ready public server needs **no Durable Objects and no session state** under the 2026-07-28 model — which matters here because this repo's Worker has no Durable Object bindings today, and adding one would be a materially bigger change than adding a stateless handler.

Sources: [Cloudflare Blog: the next generation of MCP](https://blog.cloudflare.com/mcp-v2/), [Cloudflare Agents docs: Build a Remote MCP server](https://developers.cloudflare.com/agents/model-context-protocol/guides/remote-mcp-server/), [Cloudflare Agents docs: Transport](https://developers.cloudflare.com/agents/model-context-protocol/transport/), [Cloudflare Blog: deploy remote MCP servers](https://blog.cloudflare.com/remote-model-context-protocol-servers-mcp/).

**What this means concretely for this repo**: because `/api/chat` is already an Astro API route inside the same Worker (not a separate Workers project), the lowest-friction real implementation is **not** `npm create cloudflare -- --template=remote-mcp-authless` (that scaffolds a whole separate Worker). It is a new Astro API route, e.g. `src/pages/api/mcp.ts`, implementing the stateless Streamable HTTP contract directly (JSON-RPC 2.0 over POST to `/api/mcp`, `Content-Type: application/json`, responding with either a JSON body or, for tool calls that stream, a request-scoped SSE response) using the MCP TypeScript SDK's stateless server primitives, or `createMcpHandler` from the Agents SDK if pulled in as a dependency and wired to run inside an Astro endpoint's `POST` handler. No OAuth, no KV, no Durable Object needed for a read-only, public server — the existing `CHAT_KV` rate-limit pattern from `/api/chat` could be reused verbatim for abuse control.

**Tools/resources it would sensibly expose, grounded only in `cv.yaml`** (naming mirrors the fields actually present in the file read above, not invented ones):

- `get_profile` — identity, headline, current title, employer, location, targets (maps to `identity` + `summary`).
- `search_experience(query)` — full-text search across `clinical`, `ventures`, `research.positions`, `teaching`, returning matched entries with their section heading (mirrors the citation discipline already in `prompt.ts`).
- `get_projects()` / `get_project(id)` — the `projects.items` array (SuperHuman, DermaVue Clinic OS, DermaVue Commerce, dermavue.com), including the existing `disclosure` field verbatim, since that self-reported-safety-claims caveat is load-bearing and must not get dropped by a tool response.
- `get_publications()` — the `publications` array with DOIs/PMIDs and the `research.metrics` block, sourced and dated exactly as in `cv.yaml` (`source: Google Scholar`, `asOf: September 2026`), never restated as of "today."
- `why_fit_for_role(role_description)` — the one generative tool, and the only one that should call the model at all; it should reuse `buildSystemPrompt()` from `src/chat/prompt.ts` unchanged (same refusal string, same citation rule, same rule 9 fit-comparison behavior) rather than writing a second, divergent prompt. This is the one place duplication risk is real: two prompts grounding the same CV would drift.
- `get_verifiable_credentials()` — `credentials` (board, licenses with `verifyUrl`), `honors`, `education` — useful as a distinct tool because it's the one dataset an evaluator would want to programmatically check against primary sources.
- A resource, not a tool: expose `/llms-full.txt` (or the same `renderCvMarkdown(cv)` output already used for chat grounding) as an MCP **resource** (`cv://full`) for clients that just want the whole document rather than making six tool calls — this avoids writing a second serializer.

Every one of these is a read of `cv.yaml` through the same `renderCvMarkdown`/`cv` module `/api/chat` already uses. None require new data modeling.

## 3. Beyond MCP: other 2026 agent-callable patterns

- **`agents.json`** (Wildcard/`wild-card-ai`) — a `/.well-known/agents.json` manifest describing available agent actions; real but has not displaced OpenAPI, and is oriented at transactional web actions (checkout, booking), not "here is my CV data."
- **`ai-agent.json`** (Aiia spec, published March 28, 2026) — a vendor-neutral `/.well-known/ai-agent.json` manifest for *agent identity*, i.e., declaring "this domain operates an autonomous agent," which is the wrong shape for a personal CV site (menon.md isn't itself an agent).
- **Agent Plugins 1.0** — released August 6, 2026, co-authored by AWS, Cursor, Microsoft, OpenAI, Vercel, and Google: a packaging standard (`plugin.json` + `skills/` + optional `mcp.json`) for distributing agent *tools/skills* across platforms (Claude, Cursor, Copilot, etc.). This is a packaging/distribution layer that sits on top of MCP, not a competitor to it — worth knowing about, not worth building against for a single personal site with one server.
- **A2A (Agent2Agent)**, donated to the Linux Foundation, reports 150+ supporting orgs and 22k+ GitHub stars by April 2026, but independent 2026 analyses (`agentndx.ai`, `glukhov.org`) are explicit that adoption numbers are vanity metrics — "supporter counts and GitHub stars do not tell you how many teams are running A2A in production," and no production-deployment count has been published. A2A is a task-delegation protocol between autonomous agent *systems* (e.g., a travel-booking agent orchestrating a payment agent); it has no natural fit for a static personal CV, which has no tasks to delegate.
- **WebMCP** — the most credible new-in-2026 standard, from Google/Microsoft via the W3C Web Machine Learning Community Group, accepted September 2025, shipped in Chrome Canary February 2026, now in public origin trial (Chrome 149). It lets a *page itself* expose typed JS functions to an in-browser agent (e.g., Chrome's own Gemini-in-Chrome), avoiding DOM-scraping. This is a genuinely different use case from a backend MCP server: WebMCP is for an agent *already browsing menon.md in a live browser session* (e.g., a hiring manager using an agentic browser); MCP-over-Streamable-HTTP is for an agent that connects to the site as a *tool*, independent of browsing. They are complementary, not substitutes, but WebMCP requires no server-side change (`window.navigator.modelContext` or similar registered client-side) and is a much smaller lift if the goal is "be usable by an agentic browser," which is arguably a nearer-term real audience than "a recruiter manually configures an MCP client."
- **A plain documented HTTP/JSON API + OpenAPI schema** was not specifically evidenced as a 2026 "for AI agents" trend distinct from MCP — MCP has functionally absorbed that use case for LLM tool-calling, and OpenAPI-as-agent-interface is now treated as the legacy/pre-MCP approach in every comparison article found.

## 4. What frontier labs actually say about how candidates/tools should interact agentically

Nothing found rises to a real "signal." Anthropic's own careers content (`anthropic.com/careers`, Greenhouse job posts, third-party interview-prep sites like Aced/IGotAnOffer/Yale SOM career blog) describes culture ("high-trust," "low-ego," flat hierarchy, curiosity valued) and interview *content* (agentic-systems design questions are asked of candidates), but **none of it says anything about how a candidate should present themselves to Anthropic**, agentically or otherwise. No blog post, engineering-culture page, or hiring page from Anthropic, OpenAI, or Google DeepMind was found that says or implies "expose your work this way to impress us." This should be treated as a genuine absence, not softened into a maybe. The one adjacent real fact worth keeping: Anthropic is a co-author of the MCP spec itself and clearly cares about the protocol succeeding generally — but that is evidence about their product priorities, not about hiring-signal preferences, and citing MCP-authorship as a reason "Anthropic would love this" is a stretch a technical hiring manager there would likely see through.

## 5. Honest verdict

**A CV MCP server is not table stakes, and it is not evidenced as a real differentiator either — it sits in an unusual third position: technically legitimate, currently almost unused, and high-legible to exactly the audience that would evaluate it correctly.**

The reasoning:

- It is **not** the 2026 version of "add a chatbot." The chatbot-cliché pattern is: bolt on a generic feature everyone else also bolted on, signaling nothing except "I can install a widget." An MCP server on a personal site is the opposite distribution today — real examples exist (`MCV`, the Harshdip Saha issue, several resume-MCP repos) but every one found has effectively zero adoption (0-star template, or a not-yet-built spec). Building this puts the site in a group of maybe a few dozen people globally who have done it for their own CV, not the group of thousands who added a chat widget.
- It is **not currently a functional differentiator either**, because there is no evidence any hiring team, at Anthropic or elsewhere, actually connects an MCP client to a candidate's personal server as part of evaluation. Nobody is going to `claude mcp add menon-md` during a screen. The honest claim to make about this feature is never "this will get me evaluated differently" — it's "this demonstrates fluency with the exact protocol this audience ships for a living."
- What would make it genuinely impressive versus a gimmick is entirely about **execution discipline carried over from what already exists**, not about the feature existing at all:
  1. **Spec-correctness**: 2026-07-28 stateless Streamable HTTP, not the deprecated SSE-transport pattern `MCV` still uses. Shipping the outdated transport would read, to this exact audience, as "used MCP before checking the current spec" — worse than not building it.
  2. **Zero new hallucination surface**: every tool must be a pure read of `cv.yaml` via the same `cv`/`renderCvMarkdown` module `/api/chat` already uses, and `why_fit_for_role` must reuse `buildSystemPrompt()` verbatim rather than fork a second, divergent grounding prompt. Two different "no-hallucination" contracts for the same underlying facts is itself a correctness bug.
  3. **The `disclosure` field in `projects` must survive into tool output.** `cv.yaml` already states the safety-design claims are self-reported and uncertified; an MCP tool that returns `projects.items` without that caveat would be a stricter regression than the chat, which always has the caveat in-context.
  4. **No scope creep**: read-only, no auth needed, no write tools, no "contact me" side effects — mirroring the discipline the Harshdip Saha issue's own author enforced ("exactly the two tools this spec defines and nothing more speculative").
- The stronger near-term move for "agent-callable," given the actual 2026 evidence, may be **WebMCP** rather than (or before) a backend MCP server: it targets a nearer, more plausible real audience (a hiring manager using an agentic browser to look at menon.md directly) with a much smaller implementation footprint (no new server route, no protocol compliance surface), and is a live, shipping Chrome standard rather than a pattern with zero confirmed hiring-side usage. It is not mentioned in the existing site, so it is a legitimate independent option, not a duplicate of anything already built.

## Recommendation

**Build it, but scope it as a precise, small, spec-correct addition — not a platform.** The differentiator is not "having an MCP server," it's "having a spec-correct, zero-hallucination-surface, honestly-scoped one," which is exactly the same bar the site already holds itself to on `/api/chat`. Given the current adoption evidence (near-zero real usage, no hiring-side pull), this should be framed on the site itself as a demonstration of engineering fluency, not as a promised interaction channel — do not tell visitors "recruiters will query this," because that claim is not supported by anything found in this research.

Concrete build, if greenlit:

- **New route**: `src/pages/api/mcp.ts`, an Astro API route (`prerender = false`) inside the existing Worker — not a separate `wrangler` project, not the `remote-mcp-authless` scaffold (that duplicates infra this repo already has).
- **Transport**: Streamable HTTP per spec **2026-07-28**, stateless: single `POST /api/mcp`, `Content-Type: application/json`, JSON-RPC 2.0 body; no `Mcp-Session-Id`, no long-lived SSE stream, no Durable Object. Use the MCP TypeScript SDK's stateless server mode (the same one Cloudflare's `createMcpHandler` wraps) directly in the route handler.
- **Auth**: none — public, read-only, matching the "authless" pattern Cloudflare documents as first-class supported.
- **Abuse control**: reuse the existing `CHAT_KV` rate-limit primitives from `src/chat/guards.ts` (`rateLimitKey`, `nextRateState`, fail-closed on missing KV) rather than writing new ones.
- **Tools** (all pure reads of the existing `cv` object / `renderCvMarkdown(cv)`, no new data):
  - `get_profile`
  - `search_experience(query: string)`
  - `get_projects()`, `get_project(id: string)` — must include the `disclosure` text
  - `get_publications()`
  - `get_verifiable_credentials()`
  - `why_fit_for_role(role_description: string)` — the only tool that calls the model; must call `buildSystemPrompt()` from `src/chat/prompt.ts` unmodified, same refusal string, same citation rule, same max-200-words and no-medical-advice rules, so the MCP surface and the chat surface can never give divergent answers to the same question.
- **Resource**: `cv://full` → `renderCvMarkdown(cv)`, so a client that just wants the whole document doesn't need six tool round-trips.
- **What not to build**: no write tools, no OAuth, no A2A, no `agents.json`/`ai-agent.json` manifest (wrong shape for a CV, not evidenced as adopted for this use case), no separate Durable-Object-backed session server. If any single next step is taken instead of or before this, it should be a small WebMCP client-side registration on the existing page, since it has real 2026 browser support and a plausible nearer-term audience — but that is a separate, smaller decision from the MCP server question asked here.
